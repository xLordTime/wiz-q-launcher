# Window handling in version 6

The launcher uses physical virtual-desktop pixels for native geometry. The Qt dialog renders a scaled preview of those same coordinates; it never mixes Qt logical screen sizes with Win32 placement on Windows. EnumDisplayMonitors/GetMonitorInfoW supply each display and its taskbar-aware work area. A temporary per-monitor DPI thread context is restored after each operation. For exact Windows client-area sizes, the adapter accounts for frame styles with AdjustWindowRectExForDpi (AdjustWindowRectEx fallback). Layout presets use outer rectangles. For minimized clients, editor/templates use the restored rectangle translated from workspace to physical screen coordinates, never the minimized icon rectangle.

Frame modes preserve the current frame, add a normal resizable frame, or remove decorations. The controller remembers the original managed frame bits, topmost state, outer rectangle and native WINDOWPLACEMENT. It commits recovery/undo snapshots to the existing SQLite profile before modifying a client. All controller mutations check the process name, process creation time and HWND-to-PID association. A failed batch attempts to restore changed windows, including the window whose operation failed. Native errors remain visible through the existing task error handling. Closed or reused identities are skipped during undo; cached original states are bounded.

Named profiles save account IDs and geometry, never credentials or transient HWNDs. Account templates can be prepared offline and are applied to newly started clients. Legacy rectangle lists and the legacy borderless preference remain readable. Off-screen templates recover onto an available monitor after a display is disconnected. Normal window geometry and deliberate spans remain intact.

The implementation was compared with:

- Wizwalker [client/window access](https://github.com/StarrFox/wizwalker/blob/12e64737c5a1a6bc83daf17cbde3f649ce716ff5/wizwalker/client.py) and [window utilities](https://github.com/StarrFox/wizwalker/blob/12e64737c5a1a6bc83daf17cbde3f649ce716ff5/wizwalker/utils.py).
- Deimos [client_resizing.py](https://github.com/Deimos-Wizard101/Deimos-Wizard101/blob/99194d7d053b011f2db36bcc2d2bf6635acb7d7e/src/client_resizing.py) and [window_config_dialog.py](https://github.com/Deimos-Wizard101/Deimos-Wizard101/blob/99194d7d053b011f2db36bcc2d2bf6635acb7d7e/src/gui/window_config_dialog.py). These separate OS frame/client-area sizing from game backbuffer and camera hooks.
- Microsoft [SetWindowLongPtr](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowlongptrw), [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos), and [AdjustWindowRectExForDpi](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-adjustwindowrectexfordpi).

This launcher implements OS window handling and its own native PySide6 editor. Deimos' persistent backbuffer, WndProc and camera hooks are not installed, and no wizwalker runtime dependency is required. Internal game rendering resolution is selected in Wizard101. Borderless windows are resized through the launcher editor; framed windows also have a native sizing frame. The in-app Help article explains this boundary and how to address stretched rendering or displaced clicks.

Tests cover geometry, odd-pixel rounding, negative/removed monitors, taskbar areas, preview-only edits, profile matching, offline templates, durable undo, PID/HWND reuse and partial-batch rollback. A Windows-only test runs a real Qt HWND in a separate process and checks native monitor enumeration, borderless/frame changes, exact client size, topmost, minimize and restoration without needing a Wizard101 account. Live game and mixed-DPI display tests remain necessary.
